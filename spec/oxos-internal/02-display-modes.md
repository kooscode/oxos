# Display modes (OXOS choices)

OXOS's own choices where it does not follow the reference's display behaviour (stock spec 17). First implemented
2026-10-15 (progressive CRTC), extended 2026-10-17 (HD and VGA timings, the widescreen line) and 2026-10-21 (the three
video encoders from their register maps). Code: `kernel/src/hal/av.cpp`, tables `kernel/src/hal/av_modes.inc`
(generated by `tools/gen_av_tables.py` from stock specs 18–20).

## 1. Timings per mode
The reference programs each mode from its CRTC and NV2A table rows (stock spec 17 §5, §7). OXOS does not use those
rows: it derives the NV2A timing itself.
- **SD (classes 00 / 01) on an encoder that has the row:** the timing the encoder's own row expects (the reference does
  the same: its SD totals follow the encoder's input timing, stock spec 17 §7). `tools/gen_av_tables.py` derives it
  per row:
  - Conexant: totals H_CLKI × V_LINESI; HSYNC at H_CLKI − H_BLANKI − 7 and VSYNC at V_LINESI − V_BLANKI + 1 (the
    NV2A pipeline offsets Cromwell uses on hardware); the encoder takes H_ACTIVE pixels (8 more than the framebuffer
    width on the 640 and 720 rows).
  - Focus (FS453/4 hardware reference §4): pixel clock = 27 MHz / N × M / P (× NCON / NCOD when the NCO is used);
    the input frame has the TV's field rate, its line count follows from VSC (1:1, or TV lines / (1 + VSC / 65536)
    when scaling up, TV lines / (VSC / 65536) when scaling down); the line length is clock / (field rate × lines);
    HSYNC IHO pixels and VSYNC IVO lines before the end of the line / frame; the encoder takes IHW pixels.
    Example: NTSC 640×480: 29.45 MHz, 936 × 525, HSYNC at 754.
  - Xcalibur (no datasheet; read from the rows, consistent with the standards where they apply): register 0x54 holds
    the input totals (pixels in bits 16–27, lines in 0–11; 780 × 525 for NTSC 640, 1650 × 750 for 720p); 0x56 bits
    0–11 the pixels from HSYNC to the first active pixel (260 for 720p: SMPTE 296M's HSYNC at 1390) and bits 20–31 the
    active width; 0x55 bits 0–7 the lines from VSYNC to the first active line (26 for 720p).
  CRTC and flat-panel timing are programmed alike; HSYNC is 32 pixels wide, VSYNC 3 lines.
- **HD, VGA, or SD without an encoder row:** the public standards for the picture size the mode word asks for (the mode
  words: stock spec 17 §2a): CEA-861 480p; SMPTE 296M 720p (1650×750 total); SMPTE 274M 1080i (2200×1125,
  programmed per field with CR39 = interlace half-line; the reference programs a full frame); VESA 800×600 and
  1024×768. Unknown rows fall back to 640×480.
- **Colour space:** for every encoder mode the NV2A sends YCrCb, as the encoders' rows expect (their input format is
  YCrCb; stock specs 18, 19): PRAMDAC 0x630 = 2 (YUV, as Cromwell uses it for the Xcalibur), the margin colours
  0x84C / 0x8C4 = YCrCb black (Y 0x10, Cb / Cr 0x80); RGB (all three 0) for mode bit 29, as the reference. 0x880 =
  0 (no flat-panel scaling). xemu's picture is not affected by these registers.
- High bits go to the NV extended CRTC registers CR25 (vertical bit 10s, kept with the mode across quick reboots and
  merged with the pitch bit) and CR2D (horizontal bit 8s).
- xemu sizes its display from CR01, CR12/CR07 and CR39 (doubling interlaced heights): measured 1920×1080 interlaced
  and 1280×720 for 0x880E0C03 and 0x880B0A02 (before: 640×480 for every mode).
- **Progressive output:** CR39 (interlace half-line position) must be 0xFF, as the reference leaves it: xemu treats
  any other value as interlaced and shows each field at half height (observed: Halo's menu squished into the top half
  of the window). Line compare (CR18) is likewise 0xFF (never).
- The pitch is programmed as the title passes it (for 1080i, half the line length: stock spec 17 §2a).
- Encoder modes (an SD row the encoder's tables have, or HD rows 1–3 / the Xcalibur's HD map) program the encoder
  (§3a) and the NV2A flat-panel timing; VGA modes leave the encoder alone.

## 2. The widescreen line
- OXOS writes the GPIO ports of stock spec 17 §5 step 6 (`0x80D6 ← (bit 28) | 4`, `0x80D8 ← 4`) on every mode
  change, as the reference does. xemu's "auto" aspect ratio shows 16:9 exactly when the last value written to 0x80D6
  is 5; without the write every title shows 4:3 in xemu (anamorphic pictures look squashed).
- **Deviation:** the line is also raised for 720p and 1080i mode words (HDTV table, CRTC rows 0x0A and 0x0C), which
  are always 16:9, so xemu's "auto" shows them at 16:9. Titles leave bit 28 clear in HD mode words, so on the
  reference xemu shows them at 4:3. 480p keeps the reference rule (bit 28 only), since 480p can be 4:3 or 16:9.

## 3. Encoder options
The option behaviour of stock spec 17 §5a and the encoder specs, except Macrovision: it stays off (options 1 and 0x0A
do nothing; the CGMS-A word carries level 0; the Xcalibur's mode change still writes its "Macrovision off").
Option 0x0F follows 4627 on the Conexant (register 6) and 5838 elsewhere (port 0x80C0).

## 3a. Encoder programming
- The mode change follows stock spec 17 §5 with each encoder's steps (specs 18 §1, 19 §1, 20 §3), from the tables
  of specs 18–20, except: no wait for the vertical blank phase before reprogramming, and the NV2A rows are OXOS's
  own (§1).
- **Focus:** the 5838 tables (spec 19 §5.2) and the 5838 driver (DACs off at the start of a mode change, on with
  option 9; the 5838 flicker filter mapping), since the 5838 set is the later revision.
- **Xcalibur:** the driver keeps the last value written to each register and uses it for a read-modify-write when the
  4-byte read fails (xemu models the Xcalibur as byte registers, so reads cannot return data there).
- **AV pack events** (stock spec 12 §4): the 0xBA writes on Conexant and Focus as the reference; the Xcalibur is left
  alone (the 4627 rule does not apply to it and no 5838 behaviour is documented).
- **Checks** (`make test-encoders`): Conexant and Focus registers read back as the tables have them after each mode
  set; on the Xcalibur every write must complete and the test compares the values written with spec 20.

## 4. Encoder detection
The reference decides from its own BIOS image (stock spec 17 §1). OXOS probes the bus instead, as Cerbios 3.1.0 does
(its kernel's `AvSetDisplayMode`, 0x80036FCB): an SMBus byte read (protocol 0x0A, command 0) at 0x8A, then 0xD4, then
0xE0; the first that completes (host status 0x10) is the encoder. Reason: OXOS's open BIOS has 0x70 at flash offset
0x78, and one image should serve every revision. Flags 0x20 (Focus) / 0x400 (Xcalibur) are reported exactly as the
reference would, and option 0x10 returns 0 / 1 / 2.

## 5. Xcalibur
- **SMBus (done):** the 4-byte block form (stock spec 20 §1) in the HAL, keyed by address 0xE0–0xE7 and `WordFlag`,
  so titles and the kernel see the reference's behaviour (`src/hal/smbus.cpp`).
- **Tables (done):** the pool / index scheme is a compression choice, not ABI: OXOS stores the expanded rows of stock
  spec 20 §6.2 (each entry a run of 32-bit values with its variant condition), and the row maps as the reference.

## 6. xemu notes
- Enter the Matrix in 720p or 1080i aborts xemu at render scale 2 or more (assertion in `surface_download_to_buffer`:
  one of the title's render surfaces has a pitch smaller than width × bytes per pixel, which xemu's downscale path
  rejects); at scale 1 it runs. The retail BIOS we have returns this title to the dashboard within 0.3 s in xemu, so
  there is no reference run to compare.
- xemu's display code expects the 1080i pitch convention (it divides the surface pitch by the CRTC offset).
