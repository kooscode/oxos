# Tests

`make test` (in `kernel/`) runs every phase below in xemu, on a copy of the default hard disk (the free xemu-dashboard image, fetched on first use;
`HDD_IMAGE=...` for another). The tests make no assumptions about the disk's contents beyond a formatted drive with a dashboard; each prints a `[PASS]`/`[FAIL]`
line per check and `RESULT: PASS` when all pass. Most checks come from the kernel's own boot self-tests (`tests/kernel_self_tests/*.cpp`, compiled into the
self-test build only), which leave their results in kernel variables that `boot_test.py` reads.

## Test phases (make targets)
| Target | What it checks |
|---|---|
| `make test` | The main phase: boots the self-test BIOS with a generated test disc and hard disk, and checks every milestone (CPU and HAL set-up, memory manager, scheduler, I/O, FATX, DVD and XDVDFS, EEPROM, crypto, the title loader through the kernel test title, the debug serial log). Then runs `test_dash`, `test_relaunch`, `test_fatal` and `test_udf`. |
| `make test_dash` | The release BIOS with no disc boots the dashboard from the hard disk. |
| `make test_relaunch` | The release BIOS runs the kernel test title, which restarts itself through a launch page and a quick reboot (as games do with `XLaunchNewImage`). |
| `make test_encoders` | Separate: `kernel/src/hardware/video/video_modes.inc` must match what `tools/gen_av_tables.py` makes from the encoder specs. Then on each encoder xemu can present (Conexant, Focus, Xcalibur): the probe finds it, `XboxHardwareInfo.Flags` reports it, and the dashboard's mode set writes the registers the tables give; the self-test build sets 15 mode words and the encoder options. xemu's encoder models store registers only (no picture). |
| `make test_fatal` | With no hard disk, the kernel reports a fatal error the way the original does (LED, error history in the EEPROM, code on screen). |
| `make test_format` | Separate: blank and foreign (NTFS) disks get the countdown and are formatted as exFAT at boot (the image then checked); with no dashboard, error 13; a fourth run presses X on a virtual pad on that screen and the File Manager starts. Needs `/dev/uinput`. |
| `make test_upload` | Separate: X held on a virtual pad during the boot opens the File Manager on a freshly formatted disk; xemu's network forwards a host port to it: the page, listings, an upload read back, folders created and deleted, an XBE launched. Needs `/dev/uinput`. |
| `make test_udf` | A UDF (DVD-video style) disc instead of an Xbox one: mounting and reading files from it. |
| `make test_exfat` | Separate (not part of `make test`): the self-tests on a GPT disk with one exFAT volume (256 GB, sparse, in `xemu_state/oxos_xemu_exfat/`), the test disk's C: and E: copied into folders. The FATX suite runs on E: as a folder of the volume, and X: is formatted the way Halo 2 formats its cache (64 KB clusters) and must then report what a FATX mount of that format reports; afterwards `exfat.py` checks the whole volume (spec/oxos_internal/07_exfat_driver.md). |
| `make test_lba48` | Separate (not part of `make test`): the self-tests on a 2 TB disk (a sparse copy of the test disk in `xemu_state/oxos_xemu_lba48/`). The kernel writes test sectors either side of the 28-bit limit and at the end of the disk; the test then finds each one at its exact place in the image and checks that the start of the disk is untouched (spec/oxos_internal/04_lba48.md). |
| `make test_fatx_layouts` | Separate: FATX disks as disk formatters make them (spec/oxos_internal/45 §8, §9): nine disks up to 4 TB, with and without a partition table (48-bit entries, a stale copy at the end), clusters of 16 KB to 1 MB, F: or G: to the disk's end, a small F:. Each boots the partition probe title (`partition_probe_title/`), which reports where every partition lies and writes and reads back a file on F: and G:; `fatx_layout_test.py` checks the places and reads the written file from the disk image. `ONLY_CASES=name,...` runs some disks. |
| `make test_extensions` | Separate: kernel extensions (spec/oxos_internal/34 §9.3). The test extensions (`extensions/`), the SDK's examples and the extensions OXOS ships (Universal Trainers: its menu comes up at the relaunch, a virtual pad switches the trainer on and starts the title, whose test trainer then marks it), built with the SDK as it ships, on the test disk with an `oxos_extensions.ini`; over a cold boot and two quick reboots they must keep their state pages and run their hooks, events, run loops and unloads, and the ones that fail, are refused or are not listed must be left out. |
| `make test_iso` | Separate: the ISO launcher (`tools/iso_launcher`) starts the kernel test title from a disc image on the hard disk, once per kind of image: plain, split in two, CCI, split CCI, and larger than 4 GB (spec/oxos_internal/16). |
| `make test_mcpx` | Only with `MCPX_ROM=...`: the dashboard phase again, booted through a real MCPX boot ROM. |
| `make test_controller` | Separate (not part of `make test`): every input of a virtual gamepad reaches an nxdk title (through SDL3's gamepad API) as the right Xbox controller input; then, with `oxos_igs.xos` on the disk, an in-game shortcut (BLACK + WHITE -> coldboot) and the kernel's last resort (LT + RT + BACK + BLACK held 3 s) each power the console off and on (spec/oxos_internal/48). Needs cmake, flex, bison and access to `/dev/uinput`. |
| `make test_boot_video` | Separate: the boot video (spec/oxos_internal/38): a serial-log kernel cold-booted with the boot video player, `oxos_settings.ini` and the OXOS boot video on the disk; the video plays and the dashboard follows, a button skips it (virtual pad), a missing file or player boots straight on, switched off nothing plays (`boot_video_test.py`). Needs `/dev/uinput`, ffmpeg and the PC's X display (`tools/xemu_screenshot.py`). |
| `make image_test` / `make run_image_test` | Separate: the image test title (`image_test_title/`): a picture decoded on the console, a live status panel and a changing front LED; a quick check that the kernel, a title and video work. |
| `make test_memory` | Separate (not part of `make test`): how much memory a title is given, as built (the XBE flag "limit to 64 MB", as retail games have it) and with the flag cleared; `MEMORY=128` for a 128 MB console, `MEMORY_BIOS=...` (with `MCPX_ROM=...`) to measure another BIOS. Needs nxdk, like the controller test. |
| `make test_gdb` | Separate (not part of `make test`): the GDB stub of `GDB=1` kernels. A `GDB_WAIT=1` kernel boots the gdb test title (`gdb_test_title/`) from a disc and `gdb_test.py` drives the stub over xemu's serial port as gdb does: the boot stop, a title breakpoint set before the title is loaded (the kernel's own code, which the title's addresses map at boot, left alone), Ctrl-C, threads, a single step, the library list, watchpoints split over the debug registers, `vRun` starting the title again (its library stop, the breakpoint hit in the new launch), a write watchpoint, the title's access violation, and attaching after the bug check. No gdb needed; about 10 s. |
| `make test_gdb_extension` | Separate (not part of `make test`): the GDB debugger as a kernel extension (`oxos_gdb.xos`, spec/oxos_internal/51 §3). The release kernel boots the gdb test title from a disc with `oxos_gdb.xos` enabled on the disk (`wait_for_gdb = yes`), and `gdb_test.py --extension --bridge` drives the same session as `test_gdb` from the title's start, through `tools/gdb_bridge.py` as gdb on the Modxo rig talks (the bridge passes gdb's bytes on only after the extension's `gdb: stub ready`): Ctrl-C, a title breakpoint, threads, a call, a step, the library list (`oxos_gdb.xos` in it), watchpoints in pieces, the title started again with `vRun` (the extension unloaded and loaded again, the session kept), a watchpoint, the access violation, the title's `DbgPrint`, the float registers, attaching after the bug check. About 15 s. |

## Regression run
`make regression` (in `kernel/`) runs the host unit tests (`tools/unit_tests.sh`) and then every phase above, one after another, about 15 minutes in all
(`test_exfat` alone about 8). It keeps going after a failure and ends with one summary: result, checks and time per phase, saved with each phase's log in
`build/regression/`. It fails when any phase fails, or when `test_memory` reports fewer than 15 960 free pages on a 64 MB console (OXOS's count; the stock
kernel gives 15 964, spec/oxos_internal/18 §7). `MCPX_ROM=...` adds `test_mcpx`; `ONLY=test_exfat,test_iso` runs some phases. `make release` itself runs only
the unit tests and `test_dash`.

xemu now and then freezes outright: every thread waiting, no CPU used, nothing answered on its QMP socket. So that a test fails instead of waiting for ever,
the test scripts give up on a QMP command after 60 s (`QMP_TIMEOUT` in `controller_test.py`, which `boot_test.py` and `memory_test.py` share) with
`[FAIL] xemu: no answer ... (xemu froze)` and stop xemu, and `make regression` stops a phase still running after 30 minutes (`PHASE_LIMIT_MINUTES` in
`tools/regression.py`). A frozen run is not a kernel failure: run it again.

Run it on request, and after a large change: the file systems, memory, boot, the title loader or quick reboot, or many files at once.

## Files
| File | What it is |
|---|---|
| `boot_test.py` | The test runner behind every phase except `test_controller`: makes the test disc and a copy of the hard disk, boots the BIOS in xemu, reads the results through xemu's QMP monitor and the kernel's map file, and prints the checks. |
| `kernel_self_tests/` | The kernel's boot self-tests: test code compiled into the kernel only for the self-test build (`SELFTEST=1`: `make`, `make test`), never into a release. They call kernel internals from inside the running kernel (scheduler, DPCs, timers, interrupts, I/O manager, FATX, DVD, crypto, ...) and leave their results in variables `boot_test.py` reads. `kernel_self_tests.cpp` runs them, one file per subsystem; the kernel starts them from `src/core/startup.cpp` (and holds the title back for the DVD tests in `src/titles/title_loader.cpp`). |
| `unit/` | The host unit tests of the kernel's core (GoogleTest, a 32-bit Linux build of the kernel's own sources): `tools/unit_tests.sh` runs them. [`unit/README.md`](unit/README.md), spec/oxos_internal/11. |
| `extensions/` | The test extensions for `make test_extensions`, built with the SDK: a chain of hooks, a failing load, a wrong API version, a slow run loop, an extension in plain C. |
| `kernel_test_title/` | The kernel test title: a minimal freestanding Xbox "game" run from the test disc. It checks that the kernel loads and starts titles and that the kernel functions games rely on work (clock, memory pool, disc reads, threads, drive letters, on-demand sections, SHA-1), and does the relaunch test. The comment at the top of the file lists each test. |
| `controller_test_title/` | The controller test title, built with nxdk and SDL3: shows every controller input live and records which inputs arrived, for `controller_test.py`. |
| `memory_test_title/` | The memory test title, built with nxdk and SDL3: asks the kernel how much memory there is (`MmQueryStatistics`), asks for a contiguous page above 64 MB, then allocates 1 MB blocks until the kernel refuses, noting the physical address of every page; the results are on screen and in a block `memory_test.py` reads. |
| `video_decode_title/` | The video decode test title, built with nxdk and SDL3 (`make -C kernel video_decode_title`; libmpeg2 and minimp3 fetched by `make -C kernel video_libraries`): reads every `.mpg` file next to it and times decoding, the conversion to RGB, the copy to the screen and the sound, on a console; results on the debug serial port and in `video_decode_results.txt` next to it (spec/oxos_internal/38 §4.1). |
| `boot_video_test.py` | `make test_boot_video`: cold boots of a serial-log kernel with the boot video player (`apps/oxos_boot_video`), `oxos_settings.ini` and the OXOS boot video (`make oxos_intro_video`: the boot splash picture with a tone, as an `.mpg`) on the disk, checking the kernel's and the player's log: the video plays to its end and the dashboard follows, a button skips it, a missing file and a missing player boot straight on, `boot_video_enabled = no` plays nothing (spec/oxos_internal/38 §6). |
| `memory_test.py` | The `make test_memory` runner: puts the title on a disc (once as built, once with the 64 MB flag cleared), boots the BIOS at 64 or 128 MB and prints the measurements. |
| `controller_test.py` | The `make test_controller` runner: boots the controller test title's disc, presses each input of a virtual gamepad and checks what the title received; with `--igs`, the in-game shortcuts and the last resort. |
| `virtual_gamepad.py` | A virtual gamepad through Linux uinput, which xemu sees as an ordinary USB pad. Used by `controller_test.py`, and by `boot_test.py` to press X for the File Manager. |
| `mkxiso.py` | Builds the Xbox (XDVDFS) test disc: test files plus the kernel test title as `default.xbe`. Can also pack any folder as a disc (used by `tools/debug_app.py`). |
| `mkcci.py` | Writes a CCI image (compressed disc image, Team Resurgent's libCCI `FORMAT.md`) from an ISO, for `make test_iso`. |
| `mkudf.py` | Builds the UDF test disc for `make test_udf`, covering the different ways UDF stores files and names. |
| `fatx.py` | A FATX reader for the Xbox hard-disk partitions, to check files the kernel wrote, and a small writer (`FATXWriter`: folders, files, copying a host folder) for preparing disks: `python3 tests/fatx.py SRC.qcow2 --add "E:\\Folder=host/folder" --out NEW.qcow2`. |
| `exfat.py` | Builds GPT disks with an exFAT volume (`--from-fatx SRC DST` copies a FATX disk's C: and E:) and checks a volume completely: boot and entry-set checksums, name hashes, FAT chains, no cluster used twice, the allocation bitmap (`--check IMG`, `--ls IMG /path`); `--add /F/dir=HOST` also copies a host file or folder onto a new disk. |
| `qcow2.py` | A reader for xemu's qcow2 disk images (plain and compressed), used by `fatx.py`; writes go to memory and `save()` writes a new, clean image, so the source disk is never changed. `qcow2.py --grow SRC DST 2T` makes a bigger copy of a disk (the added space is sparse). |
| `test_lzx_frames.py` | A standalone check (not part of `make test`: `python3 tests/test_lzx_frames.py`) that the BIOS packer's LZX compression (`tools/lzx.py`) decodes correctly across several frames, with `tools/lzx.py`'s own decoder and, independently, with the system's libarchive (a CAB file the test builds) when it is installed. |
